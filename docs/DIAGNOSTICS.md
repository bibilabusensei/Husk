# 这次改写处理什么

原问题的表象是 LocalDevVPN 已连接，但 Husk 停留在总括性的检查提示。VPN 已连接不能证明本机配对仍有效、DDI 能下载或挂载、helper 扩展能启动，或签名允许调试器附加。这次改写将这些情况显示为不同阶段，并记录实际发生的阶段转换。

上游 [issue #65](https://github.com/Leviidev/Husk/issues/65)包含相同检查停滞的报告；报告者的开发者签名与 App ID 调整经验可作为核对线索，不能当成每台设备都相同的根因。以这次运行实际报告为依据。

| 阶段 | 这时能确认什么 | 失败或停滞时检查 |
| --- | --- | --- |
| helper 启动 | iOS 已开始扩展请求，随后 helper 报告启动 | 完整 IPA 是否含 helper、重签是否保留扩展、App/扩展 ID 和团队是否一致。 |
| VPN 可达性 | 尝试当前 pairing 对应的设备通道 | 配对是否来自本机、重启/系统更新后是否失效、LocalDevVPN 是否实际通达。 |
| DDI 检查 / 下载 | 上游框架检查缓存或传输所需文件 | 外部下载渠道可达性、剩余空间、实际系统版本所选 DDI 格式。 |
| DDI 挂载 / 验证 | 上游实际请求挂载并验证 | 配对认证、系统接受的 DDI、Developer Mode 和设备服务响应。 |
| 调试器附加 | 准备 DDI 后等待调试器使 JIT 就绪 | 主 App 实际 `get-task-allow`、helper 生存状态、系统兼容性。 |

内置 helper 使用 NSExtension 和上游 StikJIT。扩展启动、后台存活、调试器服务和 DDI 通道依赖 iOS 行为；分阶段显示提高可诊断性，不能强迫系统允许 JIT。helper 心跳说明诊断通道活跃，不是 DDI 下载或挂载成功的证据。

## 设备验证

这套源码目前未在此 Windows 环境完成 Xcode 编译或 iPhone 运行。请在构建成功并签名安装后按以下顺序验证，记录报告与实际行为：

1. 打开 JIT 设置页并生成诊断报告，核对系统版本、当前签名和 helper 资源状态。
2. 选择内置方式，使用本机 pairing 并连接 LocalDevVPN，运行 Check setup。确认能看到真正阶段转换，最后完成结果由 helper 返回。
3. 让设备暂时无法取得网络或无法通达设备通道，确认界面给出当前阶段和处理入口。恢复条件后取消或重试，确认旧请求不覆盖新结果。
4. 在设备资源正常的情况下完成 DDI 准备与调试器连接。观察 App 报告的实际 JIT 状态，再导入一个上游明确支持且自己有权使用的 `arm64-v8a` APK 验证运行。
5. 保存当前构建 artifact 的 provenance、完整构建日志和过滤后的设备诊断。未验证的 Android 功能继续按上游边界处理。

DDI Reset 沿用上游只重置其 DDI 缓存的接口，不删除用户 APK、存档或本机 pairing 文件。重置后下一次检查仍可能需要下载、个性化和挂载。取消是向 helper 请求停止；底层同步操作可能不会立即中断，因此在旧 helper 未退出时限制重入，必要时明确提示关闭再开。

诊断导出只生成指定字段与此次操作事件。原始 `husk.log` / `husk-native.log` 可能包含路径、网络信息或框架输出，应在本机查看；它们不会自动混入此导出报告。报告中的 helper 运行签名和团队一致性如果无法从当前进程可靠确认，显示“未知”，而不是凭 profile 文件推断成功。
